# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is the documentation site for the FOG Project (a computer cloning/imaging
system), built with MkDocs + Material and published via Read the Docs at
<https://docs.fogproject.org/>. There is no application code here — this repo
is pure content (Markdown) plus the build tooling to render it.

Content is written to be dual-compatible: viewable/editable as an
[Obsidian](https://obsidian.md) vault (open the `docs/` folder as a vault) and
built as a static site by MkDocs. `docs/.obsidian/` holds vault settings.

## Commands

Build/preview locally (from repo root):

```bash
pip install -r requirements.txt
mkdocs serve   # live-reload preview at http://127.0.0.1:8000
mkdocs build   # static build; output dir is git-ignored
```

On Windows, `.\make.ps1` does the equivalent: installs/updates Python if
missing (via choco/winget), installs `requirements.txt` (skipped if already
up to date per `.lastprereqrun`), runs `mkdocs build`, then `mkdocs serve`.
The reusable logic lives in `buildFunctions.psm1` (`Get-Python`,
`Install-Requirements`, `Start-MkDocsBuild`).

There are no tests, linters, or CI config in this repo — the only
"validation" is that `mkdocs build`/`mkdocs serve` completes without errors
(broken wikilinks, duplicate `context_id`s, etc. surface as build
warnings/errors).

Production builds happen on Read the Docs per `.readthedocs.yml` (Ubuntu
22.04, Python 3.11, `pip install -r requirements.txt`, then `mkdocs build`
per `mkdocs.yml`) — not via `make.ps1`.

## Content architecture

- **Navigation** (`mkdocs.yml` `nav:`) is mostly manual, but several
  top-level sections (e.g. `installation/network-setup`, `installation/server`,
  `management/server`, `kb/*`, `development`) point at a *directory* rather
  than a file — the `mkdocs-include-dir-to-nav` plugin auto-expands those into
  a nav tree from the directory contents. Adding a new page under one of
  those directories does not require editing `mkdocs.yml`; adding a page
  under a section that lists individual files by name (e.g. Home/Getting
  Started, Web Management) does.
- **Every folder needs a `README.md`** with front matter — it serves as that
  folder's index/landing page (see the many `docs/**/README.md` files).
- **Front matter is required on every page.** Template at
  `docs/assets/templates/metadata-template.md`:
  ```yaml
  ---
  title: Page Title
  aliases:
      - Page Title
  description: brief description of the page
  context_id: unique-id-usually-matching-filename-without-extension
  tags:
      - relevant
      - tags
  ---
  ```
  `context_id` must be unique across the whole site — `hook.py` (registered
  under `hooks:` in `mkdocs.yml`) builds the redirect map from it at build
  time and logs a warning if two pages claim the same `context_id`.
- **File naming**: all lowercase, dashes not spaces (e.g.
  `plugin-schema-migrations.md`).
- **Internal links use Obsidian wikilink syntax**, rendered via the
  `roamlinks` plugin:
  - Page: `[[file-name|Friendly Title]]`
  - Heading: `[[file-name#Heading name|Friendly Title]]`
  - Image: `![[image-name.ext]]` — all images live under `docs/assets/img/`
    and are referenced by filename only (no path), so names must be unique
    site-wide.
  - **Inside a table cell, use a normal relative link**
    (`[Title](../../kb/how-tos/page.md)`), not a wikilink. The cell's `|`
    separator means the alias pipe has to be escaped, and `roamlinks` does
    not recognise `[[page\|Title]]` — it warns `unable to find page\` at
    build time and renders the wikilink as literal text on the page.
  - Don't start a line in a fenced code block with a bash `[[ ... ]]` test —
    `roamlinks` rewrites it into a markdown link (`test -d …` instead). The
    same test later in a line, or wrapped in `if`, survives; it only warns.
- **Callouts, not raw admonitions**: write Obsidian callout syntax —
  ```
  >[!note]
  >Contents
  ```
  — the `mkdocs-callouts` plugin converts these to Material admonitions at
  build time. Don't hand-write `!!! note` MkDocs admonition syntax.
- **Tags** page (`tags.md`) is generated by the `tags` plugin from each
  page's front matter `tags:` list.
- `wikiArchive/` holds the pre-migration wiki export (`.txt` files) sorted
  into `Done/`, `In-Progress-*/`, `Not-Migrating/`, `To-do/` — reference
  material for finishing the historical migration, not live docs.
- The old RST/Sphinx source has been fully removed; Markdown/MkDocs is the
  only current format (full history is still in git if ever needed).

## Documenting FOG's release/version automation

`docs/development/` documents process that lives in *other* FOGProject repos
(`fogproject`, `fog-workflows`, `fos`), not in this one — there's nothing to
run or test locally for these mechanisms. When updating these pages, keep the
cross-links between them intact:

- [`version-sync-automation.md`](docs/development/version-sync-automation.md) —
  how `FOG_VERSION`/`FOG_CHANNEL` stay correct per-branch (local pre-commit
  hook + hourly sweep workflow + `stable-releases.yml`).
- [`stable-release-workflow.md`](docs/development/stable-release-workflow.md) —
  how `dev-branch` gets promoted to a tagged `stable` release.
- [`fog-release.md`](docs/development/fog-release.md) — the manual side of a
  release (kernel/init/iPXE binary updates in the `fos` repo).

These three intentionally divide the same overall release process into
distinct concerns (version string correctness vs. the promotion pipeline vs.
manual binary updates) and each links to the others rather than repeating
content — preserve that split rather than merging them.
